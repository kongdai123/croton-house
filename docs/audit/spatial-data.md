# Spatial data audit: toward one plan model of the house

Read-only audit, 2026-10-17, repo at `2fb3130`. Nothing was edited except this file. Numbers below were computed with small
local Python scripts (point-in-polygon rasterising, bbox diffs, the repo's own `reflprobe_layout.py`), not by eye.

Conventions used in this document:

- **plan** = x east, y north, z up, metres. This is also Blender's world frame (the glTF export maps three (x,y,z) to Blender (x,-z,y), so Blender x,y == plan x,y).
- **scene** = three.js world: X = plan x, Y up, **Z = -plan y** (north is -Z). `house.js:3`, `P()` at `house.js:7`.
- "interior face" = the room side of a wall; "outer face" = the stucco/outdoor side. House.json walls are 0.1143 m (4.5 in) thick, so two sources that describe the same room by interior face vs. wall centre vs. outer face differ by 5.7 or 11.4 cm without either being wrong.
- Source column: **JSON** = read from `web/data/house.json` at runtime/bake time; **derived** = computed from JSON/geometry; **typed** = hand-typed literal.

---

## 0. Headline findings

1. There is no room model. "Which room" exists in **five independent hand-typed tables** (`rooms.js IN`, `roam.js ROOMS`, `lamp_groups.py ROOMS`, `reflprobe_layout.py ANNEX`, `layout.js` comments) plus `house.json notes`, and they disagree (section 2). `roam.js ROOMS` and `lamp_groups.py ROOMS` are byte-identical copies (checked); `rooms.js IN` is a third variant.
2. "Inside the house" has **three different definitions**, one of which (the inset rectangle `x -8.1..8.1, y -5.94/-4.82..5.62`) is copy-pasted **a dozen times** in JS, GLSL and Python (section 3).
3. The annex (garage, laundry, walk-in, vestibule closet, porch) exists only as `const` rects in `house.js` plus further hand copies in `minimap.js`, `ui.js`, `reflprobe_layout.py`, `lamp_groups.py`. The plan the bake and probe volume see (`house.json`) has no garage walls.
4. House.json is patched at build time in `house.js` (niche walls replaced, kitchen window resized, primary-bath window added) but other readers (`lightmap.js` probe walls, `reflprobe_layout.py`, `hq.js` for the non-mutated parts) see the unpatched data.
5. The **shipped** reflection-probe boxes (`web/assets/lightmaps/*/refl/meta.json`, identical in all four slots) were baked before the layout code in `bake/scripts/reflprobe_layout.py` (commit `a7f6a2a`). Probe positions differ by up to 1.45 m and boxes by up to 27 m (garage box runs 33 m north) from what the current layout code would produce. This is stale data, not a code bug, and a good argument for deriving boxes from one plan.
6. Real geometric mismatch: the **garage door gap is drawn 0.82 m east of where it is built** on both plan drawings (`minimap.js:45`, `ui.js:48`).

Reading the table:

- **Wall-thickness deltas** (about 0.11 m: kitchen/living/bedroom 3 x0, `ROOMS` y0 -4.72 and y1 5.47) are the same room measured to a different wall face (centre/outer vs. interior). They are not wrong in isolation but show nobody agreed on which face a "room rect" refers to; the rects in `ROOMS` tile the plane to the outer faces so every point gets a label, while `rooms.js`/`house.json` use interior faces.
- **Real disagreements** (not wall thickness):
  - Office/Dining split: house.json 1.119 / 1.160, `rooms.js`, `ROOMS`, layout comment at **0.42** (0.70 m apart). That point decides lamp group membership (family vs dining) and door labels. 0.42 is where the great-room dividing wall stub ends (`null-88b2e5c46a` x -2.227..0.42), so it is a defensible rule, but it is the opposite of the Zillow label placement.
  - Primary bedroom nub: house.json and `rooms.js` (second rect) put the vestibule nub (x -4.82..-3.5, y 0.77..1.6) in the primary bedroom; `ROOMS` puts it in `closets`, whose `group_of` rule then returns group **`primary`** for anything outside the walk-in x range, i.e. any light in the laundry nook or the vestibule nub is assigned to the `primary` group.

## 4. Proposal: one plan model

### 4.1 Principles

- One committed file, `web/data/plan.json` (version 1), is the only place spatial facts are written. Everything else is read from it or computed from it by a tiny reader, in **plan coordinates** (x east, y north, z up, metres), with explicit helpers for the scene frame. No code outside the two readers does the `-y` flip for plan data.
- `plan.json` is **generated** by `web/tools/build_plan.mjs` (`parse_plan.mjs` output + one authored overlay `source/plan/overlay.json`). `house.json` stays as the generated Zillow import (input only; stop reading it elsewhere once migrated). The overlay holds exactly what Zillow lacks: annex spaces and walls, outdoor zones, semantic room ids, labels (en/zh), opening types and connectivity hints, patches (niche, windows), lamp-group membership.
- Rooms are **polygons** (rectilinear, CCW, interior faces), not rects, with explicit adjacency derived from openings. Wall faces are always interior faces; wall-thickness fudges move into the readers (`dilate`).
- One validator (`web/tools/check_plan.mjs`, ~100 lines) is the guard rail: room polygons do not overlap, rooms + wall rects cover the outline with no holes, every opening links exactly two spaces, every group member has a space, bounds of generated boxes are consistent.

Heights: `levels` + per-space `ceiling` (soffit and the 2.13 m garage door stay as opening/feature data), instead of `CEIL` (house.js:6), `house.ceiling`, `daylight.js` 2.44 (twice), and `reflprobe_layout` default 2.44.

Frames and signs: only the reader exposes `toScene(x,y,z) -> [x,z,-y]`, `toPlan`. `FRONT_CLOSET_VIEW`-style data (currently in scene z) is stored in plan and converted by the reader.

### 4.3 Readers

**JS: `web/src/plan.js`** (pure data + small functions, no THREE, so Node tests and webgpu can import it; can be bundled via `import plan from '../data/plan.json'` as `lightmap.js:32` already does for house.json). API:

```js
export const plan;                                   // parsed JSON
spaceAt(x, y)            -> space | null             // point-in-polygon over spaces in priority order (annex/closets first)
roomName(x, y, lang)     -> {en, zh, outside}        // replaces rooms.js roomAt
isInside(x, y, {margin}) -> bool                     // outline dilated by margin; margin 0 = exact EXT_FP test
insideGLSL(name)         -> string                   // emits the GLSL 'outsideHouse' function from the outline's rectilinear rect decomposition (no copy-paste)
indoorWeight(x, y, h)    -> 0..1                     // signed distance to the outline polygon + the same smooth() curves
openingsOf(spaceId), neighbors(spaceId), path(a,b)   // via adjacency
wallsAt(z)               -> [{x0,x1,y0,y1,z0,z1}]    // pieces, incl. annex and patches (what lightmap.js probeWalls needs)
toScene / toPlan, sceneRect(space)                   // single place with the z flip
```

**Python: `bake/scripts/plan.py`** (stdlib only, so it runs in Blender and in `python3`; `reflprobe_layout.py` already follows this rule). Same API names: `load_plan`, `space_at`, `is_inside`, `walls_at`, `in_outline`, `adjacent`, `box_of(space, p)`, plus the reflprobe layout helpers moved over (`plan_extents` etc. stay in `reflprobe_layout.py`, but they read `plan.py`).

Both readers get the same golden tests (see 4.5), so a JS/Python divergence fails in CI.

### 4.5 Migration order and safeguards

1. **Build the data, change nothing.** Write `build_plan.mjs` and the overlay; commit `plan.json`; write `plan.js`/`plan.py`. Add `check_plan.mjs` (coverage, overlap, openings link two spaces, every `WALL_SWITCHES` and `ROOMS` group name resolves).
2. **Golden-equivalence tests before any swap.** For each old classifier (`rooms.roomAt`, `roam.areaOf/isIndoor`, `lamp_groups.room`, all inset-rect copies, `indoorWeight`), sample a 5 cm grid over x -16..16, y -16..22 (and z at 0.35/0.95/1.55 where height matters) and diff against the new reader.
